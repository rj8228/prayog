SBE: Simple Binary Encoding

The binary message format of the FIX Trading Community, used where every microsecond counts: exchange order entry, market data feeds and journals. Prayog uses it for its journal. First the idea, then the bytes, then how Prayog uses it.

1. The problem

Every order Prayog receives is written to disk before anyone is told about it. That means turning a Java object into bytes (encoding) and, on replay, bytes back into an object (decoding), millions of times a day. The format needs four properties:

  • Fast: no text parsing, no searching for field names, no allocation on the hot path.
  • Byte-stable: the same message must always give exactly the same bytes, because replay compares SHA-256 checksums of the bytes.
  • Versioned: next year's code must still read this year's journal.
  • Standard: something an engineer from any trading firm would recognise.

Text formats like JSON fail the first two. SBE was designed for exactly this list.

2. A business example: the pre-printed form

Imagine two ways a bank branch could send account-opening requests to head office.

  • A letter ("Dear Sir, please open an account for Mr. Rao, age 34..."). Flexible, but the clerk must read every word to find the age. That's JSON or FIX tag=value.
  • A pre-printed form where box 3 is always the age and box 5 is always the branch code. The clerk's eyes jump straight to box 3. Nobody reads the rest. That's SBE.

The form has one rule that matters later: you can add new boxes at the bottom, but never move or reuse an old one. Old clerks ignore the new boxes and keep working.

3. How SBE works

  1. Write an XML schema listing messages, their fields and their types (int64, uint8, enums, strings).
  2. Generate code. sbe-tool turns the schema into Java classes, one encoder and one decoder per message, at build time.
  3. Encode in place. An encoder is a flyweight: a tiny reusable object that "wraps" a buffer at an offset and writes each field straight to its fixed position. No intermediate object, no garbage.
  4. Decode in place. A decoder wraps the bytes and reads a field only when asked, by jumping to its offset. Reading the price of an order never touches the symbol.

The layout of a message

  • Header: blockLength (size of the fixed block), templateId (which message this is), schemaId and version. The header makes every message self-describing.
  • Fixed block: numbers and enums, each at a fixed offset. This is why decoding is a single memory read per field.
  • Groups: a repeated block, such as the list of instruments in Prayog's setup record.
  • Variable data: strings, as a length followed by the UTF-8 bytes. They come last and must be read in schema order, because each one starts where the previous one ended.
Byte order: Prayog's schema is little-endian, as SBE recommends. x86 and ARM are both little-endian, so encoding is a plain memory store with no byte swapping.

5. Changing a schema safely

A journal written today must replay next year. SBE supports that with a few rules:

ChangeSafe?Why
Add a field at the end of the fixed block, bump the versionYesOld decoders use blockLength from the header to skip what they don't know. New decoders see an old version and return a null value for the new field (sinceVersion).
Add a new message typeYesNew template id; old code never sees it in old journals.
Reorder or remove a fieldNoEvery later offset moves. Old bytes decode into the wrong fields.
Renumber an enum valueNoOld journals hold the old number. "SELL" would read as something else.
Reuse a template idNoOld records would decode as the new message.

This is why Prayog's schema numbers its enum values explicitly instead of trusting the Java enum's order. If someone reorders RejectReason in Java, the bytes don't change.

SBE is not a replacement for FIX; it is one of FIX's encodings. The same FIX business messages (NewOrderSingle, ExecutionReport) can be carried as text or as SBE. See the FIX page. For example, CME Group publishes its market data (MDP 3.0) and its iLink 3 order entry in SBE, and the Aeron messaging library uses SBE for its own protocols.

8. Questions

Why must strings be read in order?

A string's position depends on the length of every string before it. The decoder keeps a running "limit" that advances as each one is read. Read the symbol before the client order id and you are reading the client order id's bytes as the symbol. One of S8's planted bugs did exactly this, and the round-trip test caught it.

If SBE is so fast, why does Kafka use JSON in Prayog?

Kafka carries events to other services (post-trade, leaderboard) written in other languages, where readability and JSON Schema validation matter more than microseconds. The journal is private to the engine and on the critical path. Different jobs, different formats.

What does "zero-copy" mean here?

The decoder reads fields directly out of the buffer the bytes arrived in (or the memory-mapped journal file). Nothing is copied into an intermediate object first.
